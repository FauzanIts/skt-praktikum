B.2  Docker Compose dan Cara Service Saling Menemukan 
Pada Praktikum 1, container dijalankan satu per satu dengan docker run . Cara itu cepat merepotkan 
begitu jumlah container bertambah, karena setiap perintah harus mengingat nama image, port, dan 
variabel lingkungannya. Docker Compose menyimpan semua itu di satu file bernama docker -
compose.yml. Cukup satu perintah, docker compose up, dan seluruh container di dalam file itu dibangun 
lalu dijalankan bersama. 
Compose juga menjawab persoalan yang dibahas pada Pertemuan 2: bagaimana satu service 
menemukan service lain. Di dalam satu file Compose, setiap service otomatis bisa dihubungi memakai 
namanya. Container sensor -sim cukup menulis http://edge-api:8000, lalu  DNS internal Compose 
menerjemahkan nama edge-api menjadi alamat container yang benar. 
Nama itu hanya berlaku di dalam satu laptop. Laptop A tidak tahu apa pun tentang file Compose di 
Laptop B, sehingga edge -api tidak bisa menulis http://cloud-api. Lintas host, yang dipakai tetap 
alamat IP laptop tujuan dan port yang di -publish di sana. Alamat itu disimpan di file .env, bukan ditulis 
di kode, sesuai aturan Praktikum 1.

B.3  REST, Timeout, dan Operasi yang Aman Diulang 
REST memperlakukan  data sebagai resource yang punya alamat. Pada praktikum ini resource -nya 
adalah /bacaan di cloud-api. Menambah bacaan dilakukan dengan POST /bacaan, dan membaca daftar 
bacaan dengan GET /bacaan. Pesan dikirim sebagai JSON di atas HTTP, sehingga mudah dibaca manusia 
dan mudah diuji dari browser atau curl. 
REST bersifat sinkron: edge -api mengirim request lalu menunggu balasan. Penantian itu tidak boleh 
tanpa batas, jadi edge -api memasang timeout satu detik. Bila balasan tidak datang dalam satu detik , 
request dianggap gagal dan dikirim ulang. Kebijakan kirim ulang sampai berhasil ini disebut at -least-
once. 
Di sinilah jebakan yang dibahas pada Pertemuan 3 muncul dalam bentuk nyata. Timeout tidak berarti 
request hilang. Bisa jadi request sudah sampai dan sudah disimpan, hanya balasannya yang terlambat 
karena server sedang sibuk. Dari sisi edge-api, keduanya tampak sama: tidak ada balasan. Bila edge-api 
mengirim ulang, cloud-api menyimpan bacaan yang sama untuk kedua kalinya.

Gambar 2.3  Timeout, kirim ulang, dan data ganda 
Jalan keluarnya bukan menghapus kirim ulang, melainkan membuat operasi simpan menjadi 
idempoten: dijalankan sekali atau berkali -kali, hasil akhirnya sama. Caranya, edge -api memberi setiap 
bacaan sebuah request_id unik yang tidak berubah walau dikirim ulang. Sebelum menyimpan, cloud-api 
memeriksa apakah request_id itu sudah pernah tersimpan. Bila sudah, request tetap diterima tetapi 
tidak disimpan lagi. 
Catatan penting.  Pada Pekan 4 Anda sengaja membuat cloud -api lambat melalui variabel 
LAMBAT_PERSEN. Ini bukan kesalahan program. Ini cara memunculkan gejala yang di dunia nyata 
datang dari server yang sibuk atau jaringan yang padat. 
B.4  gRPC dan Kontrak Protocol Buffers 
gRPC adalah penerus modern RPC. Programmer memanggil fungsi seolah -olah fungsi lokal, misalnya 
stub.Kirim(bacaan), padahal fungsi itu dijalankan di laptop lain. Yang membedakannya dari REST 
adalah urutan kerjanya: kontrak ditulis lebih dulu, kode menyusul. 
Kontrak ditulis dalam file .proto memakai bahasa Protocol Buffers. File itu menyebutkan fungsi apa saja 
yang tersedia dan seperti apa bentuk pesannya. Dari satu file .proto, alat grpc_tools.protoc 
membangkitkan dua file Python. File sensor_pb2.py berisi kelas pesan, dan sensor_pb2_grpc.py berisi 
stub untuk client serta kerangka servicer untuk server. Kedua laptop harus memakai salinan file .proto 
yang identik.

Setiap field di file .proto diberi nomor, misalnya double nilai = 2 . Nomor inilah, bukan nama field,

B.5  MQTT, Publish–Subscribe, dan Persistent Session 
REST dan gRPC menuntut pengirim dan penerima hidup pada saat yang sama. Bila cloud-api mati, edge-
api hanya bisa mencoba lagi lalu menyerah. MQTT melepaskan syarat itu dengan menaruh perantara di 
tengah, yaitu broker. Pada praktikum ini broker-nya adalah mosquitto, yang berjalan sebagai container 
di Laptop B. 
Pengirim, disebut publisher, menulis pesan ke sebuah topic, misalnya skt/laptop-a/suhu. Penerima, 
disebut subscriber, berlangganan topic yang ia minati. Tanda + pada skt/+/suhu berarti satu tingkat  
topic apa pun, sehingga cloud -api menerima suhu dari semua node. Publisher tidak tahu siapa 
subscriber-nya, dan tidak menunggu pesannya diproses. 
MQTT mengenal tiga tingkat jaminan pengiriman yang disebut QoS. Namanya mirip istilah semantik 
pemanggilan pada slide Pertemuan 3, tetapi padanannya tidak persis sama. Tabel berikut 
menyelaraskan keduanya agar tidak tertukar.

B.6  GraphQL: Membaca Data Sesuai Kebutuhan 
Tiga pola sebelumnya dipakai untuk mengirim data dari edge ke cloud. GraphQL dipakai di sisi lain, yaitu 
membaca data yang sudah terkumpul. Pada REST, bentuk balasan ditentukan server. GET /bacaan selalu 
mengembalikan semua field, walau aplikasi yang memanggil hanya butuh dua. Kebutuhan lain, seperti 
rata-rata suhu, memerlukan endpoint tersendiri. 
GraphQL membalik aturan itu. Server menyediakan satu endpoint, /graphql, beserta schema yang 
menjelaskan data apa saja yang bisa diminta. Client menulis query yang menyebutkan field yang ia 
butuhkan, dan server mengembalikan tepat field itu. Setiap field dalam schema dilayani oleh sebuah 
fungsi yang disebut resolver.

C.4  Membangun cloud-api di Laptop B 
cloud-api menerima bacaan dan menyimpannya di database SQLite. Mulailah dari file yang mengurus 
penyimpanan. Bagian terpenting ada di fungsi simpan. Bila IDEMPOTEN bernilai 1, request_id diperiksa

perlambatan itu terjadi setelah data tersimpan.

import random 
import sqlite3 
import threading 
import time

def statistik(): 
    with _kunci: 
        total, unik = _db.execute( 
            "SELECT COUNT(*), COUNT(DISTINCT request_id) FROM bacaan").fetchone() 
    return {"baris_tersimpan": total, "request_id_unik": unik, 
            "data_ganda": total - unik} 
  
  
def ambil(terakhir=10, node_id=None, jalur=None): 
    with _kunci: 
        baris = _db.execute( 
            "SELECT * FROM bacaan" 
            " WHERE (? IS NULL OR node_id = ?) AND (? IS NULL OR jalur = ?)" 
            " ORDER BY id DESC LIMIT ?", 
            (node_id, node_id, jalur, jalur, terakhir)).fetchall() 
    return [dict(b) for b in baris] 
  
  
def ringkasan(node_id=None): 
    with _kunci: 
        n, rata, mn, mx = _db.execute( 
            "SELECT COUNT(*), AVG(nilai), MIN(nilai), MAX(nilai) FROM bacaan"

import os

log = logging.getLogger("uvicorn.error") 
  
  
def kirim_rest(pesan): 
    url = f"http://{CLOUD_HOST}:9090/bacaan" 
    for coba in range(1, MAKS_COBA + 1): 
        try: 
            r = httpx.post(url, json=pesan, timeout=TIMEOUT_S) 
            log.info("REST seq=%s coba=%s -> %s %s", 
                     pesan["seq"], coba, r.status_code, r.text) 
            return {"terkirim": True, "coba": coba} 
        except httpx.TimeoutException: 
            log.warning("REST seq=%s coba=%s -> timeout, kirim ulang", 
                        pesan["seq"], coba) 
        except httpx.TransportError as e: 
            log.warning("REST seq=%s coba=%s -> gagal terhubung (%s)", 
                        pesan["seq"], coba, type(e).__name__) 
    return {"terkirim": False, "coba": MAKS_COBA}

from concurrent import futures 
  
import grpc 
  
import penyimpanan as db 
import sensor_pb2 
import sensor_pb2_grpc

class SensorServicer(sensor_pb2_grpc.SensorServicer): 
    def Kirim(self, request, context): 
        pesan = { 
            "request_id": request.request_id, 
            "node_id": request.node_id, 
            "seq": request.seq, 
            "nilai": request.nilai, 
            "waktu": request.waktu, 
        } 
        hasil = db.simpan(pesan, jalur="grpc") 
        return sensor_pb2.Status(diterima=True, duplikat=hasil["duplikat"])

    global _server 
    _server = grpc.server(futures.ThreadPoolExecutor(max_workers=10)) 
    sensor_pb2_grpc.add_SensorServicer_to_server(SensorServicer(), _server) 
    _server.add_insecure_port(f"0.0.0.0:{port}")  # ingat pelajaran Praktikum 1 
    _server.start()

C.9  Mengukur REST dan gRPC 
Program ukur_protokol.py mengirim 200 bacaan lewat REST, lalu 200 bacaan lewat gRPC. Setiap jalur

sebelum mengukur. 
import json 
import os

import time 
import uuid 
  
import grpc 
import httpx 
  
import sensor_pb2 
import sensor_pb2_grpc 
  
CLOUD_HOST = os.environ["CLOUD_HOST"] 
JUMLAH = 200 
  
  
def pesan_contoh(i): 
    return {"request_id": str(uuid.uuid4()), "node_id": "uji-ukur", 
            "seq": i, "nilai": 29.75, "waktu": int(time.time() * 1000)} 
  
  
def ringkas(nama, data_ms): 
    data_ms.sort() 
    p50 = statistics.median(data_ms) 
    p95 = data_ms[int(0.95 * len(data_ms)) - 1] 
    print(f"{nama:<5} RTT p50 = {p50:6.2f} ms   p95 = {p95:6.2f} ms") 
  
  
contoh = pesan_contoh(0) 
ukuran_json = len(json.dumps(contoh).encode("utf-8")) 
ukuran_pb = len(sensor_pb2.Bacaan(**contoh).SerializeToString()) 
print(f"ukuran satu pesan : JSON = {ukuran_json} byte, Protobuf = {ukuran_pb} byte") 
  
# REST: satu koneksi dipakai ulang agar adil 
with httpx.Client(timeout=5) as klien: 
    url = f"http://{CLOUD_HOST}:9090/bacaan" 
    klien.post(url, json=pesan_contoh(0))  # pemanasan 
    hasil = [] 
    for i in range(1, JUMLAH + 1): 
        t1 = time.perf_counter() 
        klien.post(url, json=pesan_contoh(i)) 
        hasil.append((time.perf_counter() - t1) * 1000) 
    ringkas("REST", hasil)

import logging 
import os 
  
import paho.mqtt.client as mqtt

def _saat_terhubung(client, userdata, flags, reason_code, properties): 
    log.info("MQTT terhubung (session_present=%s)", flags.session_present) 
    client.subscribe("skt/+/suhu", qos=1) 
  
  
def _saat_pesan(client, userdata, msg): 
    pesan = json.loads(msg.payload) 
    hasil = db.simpan(pesan, jalur="mqtt") 
    log.info("MQTT seq=%s -> %s", pesan["seq"], hasil) 
  
  
def mulai_mqtt(): 
    global _klien 
    _klien = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, 
                         client_id="cloud-api-subscriber", 
                         clean_session=False) 
    _klien.on_connect = _saat_terhubung 
    _klien.on_message = _saat_pesan 
    _klien.connect_async(MQTT_HOST, 1883) 
    _klien.loop_start()
